## 1. Power-loss publication guarantees — REQUIRE CRASH-SAFE DURABLE PUBLICATION, NOT A HARDWARE GUARANTEE

Seal 07 does not need to claim survival against every possible storage-controller or filesystem failure.

It **does** need to guarantee that Bytefray's publication sequence does not intentionally expose a partially written canonical record as though it were complete.

For durable write-once records participating in the F2 recovery path:

- construct the complete canonical bytes before publication;
- write them to a distinct temporary/staging destination in the same durable location/filesystem where practical;
- flush the file contents before publication;
- publish into the canonical destination using the strongest atomic replacement/rename primitive compatible with the existing write-once semantics;
- once the canonical destination exists, never overwrite it;
- where the platform/filesystem supports directory metadata flushing, use it if the existing project abstraction can do so without introducing an unbounded cross-platform dependency;
- if the platform cannot provide a meaningful directory flush primitive, record that limitation rather than pretending full physical-power-loss durability is guaranteed.

The scientific guarantee is therefore:

**after restart, the canonical path must be either absent or contain a complete canonical record; Bytefray must not intentionally leave a half-record at the canonical path.**

Do not claim immunity to arbitrary hardware, filesystem, controller, or OS corruption outside that model.

This applies to the Seal-07 crash-consistency records identified in Revision 02, including PASS and verification-result publication where those records participate in recovery.

## 2. Concurrent replacement threat boundary — OUTSIDE ADVERSARIAL THREAT MODEL, BUT DETECT ORDINARY RACES

Do not expand Seal 07 into protection against an attacker with arbitrary concurrent filesystem write access.

The threat model for this revision may assume no hostile actor is deliberately replacing paths between validation and open.

However, the implementation must still defend against ordinary filesystem races where practical:

- reject unsupported non-regular objects before potentially blocking reads;
- re-check the opened object/type or identity where the implementation already has enough information to do so;
- validate bytes/digests after reading;
- fail closed if the object actually consumed does not match the expected retained identity.

A check/open race caused by an adversary with arbitrary filesystem mutation capability remains a documented residual.

Do not claim that the pre-check + `Path.open` design prevents malicious TOCTOU replacement.

This residual is acceptable for Seal 07 because arbitrary hostile filesystem write access is outside the current E9 evidence model.

## 3. Legacy torn destinations — DO NOT AUTO-REPAIR AMBIGUOUS PRE-SEAL ARTIFACTS

Distinguish two cases.

### A. Torn artifact created under the new Seal-07 publication/recovery protocol

Recover according to the newly qualified crash-recovery rules.

If the retained state proves that:

- the same scientific inputs are being used;
- the canonical intended bytes can be re-derived exactly;
- no disqualifying authority event intervened;
- no contradictory terminal outcome exists;

then exact recovery may complete the missing durable transition without rewriting scientific material.

### B. Legacy torn or malformed destination whose provenance cannot be established under the Seal-07 recovery protocol

Do **not** infer that it was merely an interrupted write.

Do not delete it, overwrite it, or automatically convert it into a valid record.

Treat it as a non-operational legacy/ambiguous state requiring separate disposition.

Seal 07 should not create a migration/repair mechanism for arbitrary old malformed evidence.

Qualification may create controlled torn artifacts representing the exact newly authorized crash points, because their provenance is known by the test.

This keeps the recovery rule narrow: **recover known interrupted transitions, not unexplained damaged history.**

- require no intervening authority event, including HOLD;
